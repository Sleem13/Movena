# Progress report journey

## Patient concept

Progress keeps analysis history first and presents clinician-created reports as a
second white surface. Each report shows a localized start/end period and one clear
Open report action. Only reports explicitly shared by the clinician appear. Signed
legacy artifact paths are rewritten through the authenticated replacement API so a
relative v1 link cannot bypass the new client boundary.

Loading uses the shared progress indicator and live status label. The empty state
states that no report has been shared. API and launch failures stay in the report
surface with a retry action. Opening uses a new browser/app surface so the user's
current recovery context remains available. Expired signed artifacts return the
standard dependency error and can be regenerated by the care team.

## Therapist concept

The selected-patient review surface places Create progress report beside Care plans.
The form defaults to the last 30 local calendar days, limits the period to 366 days,
and leaves patient sharing off. Start and end labels remain explicit in RTL. Success
shows one next action to open the generated report. A denied or revoked care
relationship never creates an artifact or report record.

## Components and accessibility

- `ProgressReportForm` / `CreateProgressReportView`: two native date inputs, explicit
  sharing checkbox, inline validation, busy fieldset, success/error live regions.
- `PatientReportsPanel`: localized period row and safe external open action.
- `reportHref` / `reportUri`: allow HTTP(S), reject credentials and unsafe schemes,
  and translate signed `/api/v1/artifacts/` paths to `/api/v2` client routes.
- Controls inherit the shared 48-point minimum target, scalable typography, visible
  focus, dark tokens and platform reduced-motion behavior.

## Acceptance states

English and Arabic must preserve calendar dates without timezone shifts. The empty,
loading, denied, invalid-period, generation-error, ready and expired-artifact states
must remain distinct. Patient visibility and assigned-clinician authorization are
verified at the API rather than inferred from the screen.
